# Releasing

One tag drives every channel. Push `v0.1.0` and CI builds a binary per platform,
publishes the npm packages, creates the GitHub Release, and bumps the Homebrew
formula from the same assets.

## What ships

| Artifact                         | Where it goes  | Who consumes it                                               |
| -------------------------------- | -------------- | ------------------------------------------------------------- |
| `sentry-tui-<platform>.tar.gz`   | GitHub Release | `install.sh`, Homebrew, manual download                       |
| `checksums.txt`                  | GitHub Release | `install.sh` and the formula, both of which verify against it |
| `@billyvg/sentry-tui-<platform>` | npm            | optional dependency, one binary each                          |
| `@billyvg/sentry-tui`            | npm            | the launcher — the package everything else points at          |
| `sentry-tui`                     | npm            | unscoped alias, so `npx sentry-tui` works                     |

The repo's own `package.json` is `private` and never published. Every published
manifest is generated by `scripts/build-npm.ts`, which keeps devDependencies,
git hooks, and the source layout out of the tarballs. The platform list lives in
`scripts/release-targets.ts`; `scripts/packaging.test.ts` fails if the workflow
matrix, the launcher's lookup table, or the installer drift away from it.

## Why prebuilt binaries

OpenTUI's renderer is native code reached through `bun:ffi`. Its Node backend
needs `node:ffi` — Node 26.1+, behind `--experimental-ffi` — so shipping source
and hoping the user's runtime cooperates isn't viable. `bun build --compile`
embeds the runtime _and_ `libopentui`, which makes each binary standalone
(~70MB on disk, ~24MB compressed) and lets a single artifact serve npm,
Homebrew, and the shell installer alike.

Cross-compiling is deliberately not attempted: `bun build --compile --target=X`
must resolve `@opentui/core-<X>`, and `bun install` skips packages whose
`os`/`cpu` don't match the host. Hence one native runner per target.

## One-time setup

1. **npm account.** `npm login` as `billyvg`, and confirm with `npm whoami`.
   Nothing is published from a laptop except by the manual path below.
2. **`NPM_TOKEN` secret.** On npmjs.com, Access Tokens → Generate → **Granular**
   (or Classic → Automation), with publish rights. Add it to the repo as
   `NPM_TOKEN` under Settings → Secrets and variables → Actions. Publishing uses
   `--provenance`, which also needs the `id-token: write` permission the release
   job already grants.
3. **Homebrew tap.** Create `billyvg/homebrew-tap` (a public repo — Homebrew
   requires the `homebrew-` prefix). Add a `HOMEBREW_TAP_TOKEN` secret holding a
   PAT with write access to it; the default `GITHUB_TOKEN` cannot reach another
   repository. Without that secret the tap step is skipped and the rest of the
   release still runs.

## Cutting a release

```bash
# 1. Bump the single source of truth.
#    scripts/build-npm.ts stamps every generated manifest from this.
$EDITOR package.json          # "version": "0.2.0"

# 2. Verify.
bun run check
bun run test:packaging

# 3. Commit, tag, push. The tag must match the version or CI fails the run.
git commit -am "chore: release v0.2.0"
git tag v0.2.0
git push origin main --tags
```

Watch the run in Actions. It builds four binaries — macOS and Linux, arm64 and
x64 — smoke-tests each with `--help` on its own runner, then publishes.

### Rehearsing without publishing

Actions → Release → Run workflow, with `dry_run` checked. It builds and packages
everything, publishes nothing, and uploads `dist/release`, `dist/npm`, and
`dist/homebrew` as an artifact you can inspect.

### Publishing by hand

You cannot build a full release on one machine — each target needs its own
runner — so a manual publish still starts from a CI build. Run the workflow with
`dry_run` checked, download the `release-bundle` artifact, and publish the
package trees inside it:

```bash
unzip release-bundle.zip -d bundle    # gives bundle/dist/npm/…
cd bundle/dist

# Platform packages first, then the launcher, then the alias: each depends on
# the ones before it.
for pkg in npm/billyvg-sentry-tui-*; do npm publish "$pkg" --access public; done
npm publish npm/billyvg-sentry-tui --access public
npm publish npm/sentry-tui --access public
```

Add `--dry-run` to any of those to see the file list and computed tarball
without uploading. Manual publishes have no provenance attestation — CI
publishes do.

Publishing only the platform package you can build locally is a trap worth
naming: the other platforms' optional dependencies simply won't resolve, and
users there get the launcher's "binary package missing" error instead of a
working install.

## Verifying a release

```bash
npx sentry-tui@latest --help
curl -fsSL https://raw.githubusercontent.com/billyvg/sentry-tui/main/install.sh | bash
brew install billyvg/tap/sentry-tui && sentry-tui --help
```

To exercise the installer without a published release, serve the assets locally
and point it at them:

```bash
SENTRY_TUI_BASE_URL=http://127.0.0.1:8731 \
SENTRY_TUI_VERSION=v0.2.0 \
SENTRY_TUI_INSTALL_DIR=/tmp/stui \
  bash install.sh
```

## Adding a platform

1. Add the target to `RELEASE_TARGETS` in `scripts/release-targets.ts`.
2. Add the matching `- target:` entry to the matrix in
   `.github/workflows/release.yml`.
3. Add the mapping to `PLATFORM_PACKAGES` in `packaging/npm/launch.mjs`.
4. `bun run test:packaging` — it tells you anything still out of step.

Two gaps are deliberate.

**Windows.** Nothing here has been run against a Windows terminal, and a binary
nobody has tried is worse than no binary. Adding it means a `win32-x64` target on
`windows-latest`, widening `ReleaseTarget["os"]`, teaching the launcher and
`build-npm.ts` about a `.exe` suffix, and shipping the asset as a `.zip` — plus
someone actually driving the TUI on Windows Terminal first.

**musl Linux.** Needs `bun-linux-{x64,arm64}-musl` builds, an Alpine runner or
container, and packages carrying npm's `libc` field; the launcher would also have
to detect musl at runtime rather than trusting `process.platform`.
